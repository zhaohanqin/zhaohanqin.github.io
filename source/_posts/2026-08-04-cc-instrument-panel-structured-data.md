一张仪器面板截图里同时存在表格区域、红蓝曲线、试管编号、横纵坐标文字和峰形。它们看起来都在同一张图上，却属于完全不同的视觉问题：区域定位需要分割，曲线需要像素级追踪，文字需要 OCR，坐标刻度需要拟合，峰值则需要结合曲线形状和坐标语义。

这个项目把截图逐层转换为稳定 JSON：先定位主画布，再提取红蓝曲线和试管编号，根据需要读取横轴，对纵轴百分比建立映射，最后检测峰并归属到试管。工程重点不是“调用一个大模型识别整张图”，而是让每个阶段都能替换、降级和检查。

## 1. 为什么不能只做一次 OCR

OCR 擅长把局部文字图像变成字符串，却不能自动回答：

- 哪个矩形是主表格；
- 红线和蓝线分别经过哪些像素；
- 某个文字属于试管号、横轴还是纵轴；
- 纵轴数字和曲线高度如何对应；
- 峰属于哪个试管区间；
- 当前横轴范围是否需要重新建议。

项目因此把问题分成六个有明确输入输出的模块：

| 模块 | 输入 | 输出 | 主要风险 |
|---|---|---|---|
| 表格/画布定位 | 完整截图 | table mask 与 ROI | 边界偏移会影响所有下游 |
| 红蓝曲线处理 | ROI | mask、轨迹点列 | 颜色变化、断线、交叉 |
| 试管 OCR | 试管条带 crop | 编号 token 与位置 | 版本/API、字符错识 |
| rescale 判定 | 试管序列、可选横轴 OCR | `need_rescale` 与建议范围 | token 错误传导 |
| percent 映射 | 纵轴 OCR 与几何位置 | 像素 y 到 percent 的映射 | 刻度缺失、拟合错误 |
| peak 后处理 | 曲线、轴映射、试管边界 | 峰位置、高宽、percent、归属 | 阈值与坐标依赖 |

## 2. 表格定位：先建立可信的局部坐标系

主程序先缩放输入到统一参考尺寸，再定位右侧表格/曲线画布。当前代码支持多种后端：

- YOLO 表格实例分割；
- SAM3 文本提示分割；
- 部分几何和后处理回退。

定位结果不是最终框，而是经过边界修正的 mask 和 ROI。后续曲线追踪、OCR crop 和轴位置全部建立在这个局部坐标系上。

这解释了为什么表格模型的错误具有系统性：如果 ROI 向左偏移，曲线、刻度和试管区域的所有坐标都一起偏；如果只看最终峰数量，很难知道问题发生在最前面的区域定位。

## 3. 红蓝曲线采用不同信息源

项目没有假设两条曲线必须由同一种模型处理。红线和蓝线可以选择不同后端：

| 对象 | 可见实现路径 | 设计考虑 |
|---|---|---|
| 表格 | YOLO / SAM3 / 几何修正 | 区域级实例与边界 |
| 红线 | SAM3 / 颜色过滤 / 可选 U-Net | 红色域明显时可用轻量规则 |
| 蓝线 | ResNet34 U-Net / SAM3 / HSV | 蓝线细、可能断裂，需要像素级恢复 |

颜色过滤并不等于“简单找红色像素”。实际需要考虑色域、亮度、连通性、曲线宽度和表格背景。U-Net 路径则把问题当成二值分割，再将 mask 后处理成单值轨迹。

曲线处理阶段只负责恢复轨迹，不在这里直接决定峰。把“分割”和“峰解释”分开，可以独立检查曲线是否正确，也能在不重训分割模型的情况下调整峰检测策略。

## 4. OCR 兼容性为什么成为工程问题

项目经历过 PaddleOCR 2.x 风格调用与 3.x 环境不兼容的问题。旧代码假设可以调用带 `cls=False`、`det=False` 的高层接口，实际环境中的 PaddleOCR/PaddlePaddle 组合改变了调用和模型目录要求，导致：

- 试管 OCR 报未知参数；
- 高层 `predict()` 路径触发推理后端问题；
- y/x 轴 OCR 为空，继而让 percent 映射和峰结果为空。

最终代码统一到一条显式链路：

```text
文字检测模型
  -> bbox
  -> 按 bbox 裁剪 crop
  -> 文字识别模型
  -> token + 位置 + 置信信息
```

检查到的版本约定为 PaddlePaddle 3.3.0、PaddleOCR 3.4.0，并使用传统 det/rec 模型。试管、纵轴和横轴复用同一兼容入口，避免三个模块各自维护旧 API。

默认还固定在 CPU 并关闭 MKL-DNN，以绕开当时环境中的推理兼容问题。这是特定环境下的稳定性选择，不代表 CPU 永远比 GPU 更适合 OCR。

## 5. `need_rescale` 是一个条件分支

试管编号 OCR 后，`judge` 模块检查编号递增性、重复/重叠等结构信号，给出 `need_rescale`。只有为真时，程序才进一步读取横轴并计算推荐范围。

这形成一个节省计算并减少无谓 OCR 的条件分支：

```text
tube tokens
  -> judge
  -> need_rescale = false -> 保留当前范围语义
  -> need_rescale = true  -> x 轴 OCR -> 拟合/推荐范围
```

`need_rescale` 不是图像质量分数，也不意味着整张图识别成功。它只表达当前规则下是否需要进行横轴范围处理。

## 6. 纵轴百分比如何映射到曲线像素

纵轴 OCR 提供若干配对点：图像纵坐标 `y_i` 与读到的百分比 `p_i`。后处理会清理异常 token，建立像素位置到百分比的映射。可将其理解为拟合：

```text
p(y) = a*y + b
```

真实实现还要处理 OCR 缺失、刻度顺序、重复值和坐标范围。如果 `0%` 位置无法确定，后面的峰高度与 percent 就失去参考。

这也是此前出现“peak=0”的根因之一：不是峰算法突然失效，而是 y 轴和 x 轴 OCR 仍走旧接口，导致 `axis_percent_map、fit_line、x_values` 为空。这个排障过程说明，端到端视觉系统的错误常发生在模块边界，而不是最后报错的位置。

## 7. 峰值检测与试管归属

曲线追踪输出按 x 排列的 y 坐标。峰模块以纵轴 `0%` 位置为参考，把图像坐标转换为曲线高度信号，再使用连续小波变换（CWT）等规则寻找候选峰。

一个候选峰需要结合：

- 峰顶横坐标；
- 相对基线高度；
- 左右边界或峰宽；
- 映射后的 percent；
- 所在试管编号区间。

CWT 通过不同尺度的波形响应寻找局部凸起，适合同时出现窄峰和宽峰的情况。但尺度、显著性和后处理阈值都会影响结果。峰检测输出是图像信号特征，不直接等同于化学结论。

## 8. 稳定 JSON 契约

项目明确把对外字段作为兼容边界。精简结果至少保留：

```json
{
  "peak": {
    "curve_peaks": {
      "items": [
        {
          "peak_index": 1,
          "height": 0.0,
          "percent_value": 0.0
        }
      ]
    }
  },
  "rescale": {
    "need_rescale": false
  }
}
```

这是字段结构示意，不是真实样本值。中间阶段可以扩展更多调试信息，但 compact 后的关键字段不能随算法重构任意改变，否则下游服务会被破坏。

每张图最终只保留 `*_result.png` 和 `*_result.json`，其他 mask、crop 和临时文件在后处理完成后清理。这样适合生产集成，却也带来一个研究复现问题：若不另外保存运行清单和中间产物，出现异常时很难追溯是哪一级失败。

## 9. 已保存的资源基准结果

仓库保留了一份 2026-07-14 的受控基准文档。测试条件是：RTX 4090、Python 3.10、8 张测试图、OCR 关闭、蓝线都使用 ResNet34 U-Net。对比：

- A：表格 SAM3 + 红线 SAM3；
- B：表格 YOLO + 红线颜色过滤，完全不加载 SAM3。

*图 2：仓库基准文档记录的受限对比。数字只适用于上述 8 图、OCR 关闭和指定硬件/后端条件。*

| 指标 | A：SAM3 + SAM3 | B：YOLO + color filter | 文档记录的差异 |
|---|---:|---:|---:|
| 峰值 GPU 显存 | 2665 MiB | 899 MiB | -1766 MiB |

但这不是完整质量比较：OCR 被关闭，文档明确没有做像素级质量对比；原始 `summary.json/csv` 和输入图没有随当前树一同保留。因此这些数字可以作为“该次受限基准记录”，不能泛化为所有机器、分辨率或完整端到端速度，也不能说明 B 的识别质量更好。

## 10. CC-only 与专家优先级对比

另一个统计文档记录了 11 个可比 MED 样本上的“首选峰/送检优先级”对比：

| 指标 | 文档记录值 | 定义 |
|---|---:|---|
| Top-1 一致率 | 100%（11/11） | 专家与 API 的最优先峰编号相同 |
| 平均 Spearman rho | 约 0.946 | 共同非空峰位上的优先级秩相关 |
| 平均 L1 | 约 0.636 | 每个样本的对应峰秩差绝对值之和，再取平均 |

Spearman 的计算不是对峰索引排序，而是把专家与 API 已有的优先级数字作为配对样本，分别取秩后计算 Pearson 相关。Top-1 遇到并列时，选择峰编号更小者。

这组结果同样需要限定：原始对照 CSV、API 回填行和机器可读汇总没有出现在当前仓库树中，无法在本次审计中重算。样本只有 11 个，不能推断普遍准确率。它适合作为一个已有内部实验记录，并指明下一次应补齐的原始结果包。

## 11. 训练记录能说明什么

仓库还保留了表格分割训练 CSV，包含 160 个 epoch 的 box/mask precision、recall、mAP 和损失；蓝线 U-Net 目录也保存了若干训练日志和权重。

这些文件证明训练过程曾输出指标，但数据来源、划分、随机种子、最佳 checkpoint 选择和独立测试协议并不完整。训练/验证指标很高也不能自动证明没有数据泄漏或能泛化到新设备。因此本文不把某个 epoch 的 mAP 当成最终系统准确率。

## 12. 降级输出与可运维性

红线处理失败时，项目提供降级 PNG/JSON 路径，让单图失败不会直接中断整个批处理。批量终端会输出每图耗时和最终 summary。

这是一种可运维设计，但仍需真实失败夹具验证以下语义：

- 降级结果能否被下游正确区分；
- 清理中间文件后是否保留足够诊断信息；
- OCR、表格和曲线不同失败是否有稳定错误码；
- 批处理中单图异常是否污染后续模型状态。

## 13. 技术栈

| 层次 | 技术 | 用途 |
|---|---|---|
| 深度学习 | PyTorch、YOLO、SAM3、ResNet34 U-Net | 表格与曲线分割的可替换后端 |
| OCR | PaddleOCR / PaddlePaddle | 试管号和横纵轴文字 |
| 图像处理 | OpenCV、NumPy | ROI、颜色过滤、曲线追踪、坐标映射、绘图 |
| 信号处理 | CWT 与规则后处理 | 峰候选、峰宽、高度和归属 |
| 工程契约 | CLI、JSON、降级输出 | 与下游服务保持稳定接口 |

## 14. 下一步怎样形成完整证据链

当前最需要的不是再增加一个识别后端，而是建立三层评测：

1. **模块级**：表格 IoU、红蓝曲线像素误差、OCR 字符/序列准确率、轴拟合残差；
2. **结构级**：峰数量、峰位置、高宽和试管归属误差；
3. **业务输出级**：优先级 Top-k、排序相关与失败样本分类。

每个结果包都应保存输入授权状态、代码提交、后端组合、模型哈希、OCR 开关、环境、完整 JSON 和最终图。资源基准与质量评测必须在同一开关下分别报告，避免用“更快”暗示“更准”。

这个项目的核心价值，是把一个复杂仪器截图拆成了可替换、可降级、可通过稳定契约交付的视觉系统。已保存的两份实验文档提供了初步资源和排序证据；下一步需要补齐原始包与端到端质量标注，让每个漂亮数字都能被重新计算。
